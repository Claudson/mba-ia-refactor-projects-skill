  Findings

  F01 [CRITICAL] Credenciais de produção e chave de gateway hardcoded

  File: src/utils.js:2-5
  Catalog: AP-01 — Credenciais / Segredos Hardcoded
  Description: O objeto config contém os literais dbPass: 
  "senha_super_secreta_prod_123", dbUser: "admin_master", paymentGatewayKey: 
  "pk_live_1234567890abcdef" (prefixo de chave live) e smtpUser, além de port: 
  3000 fixa.
  Impact: Quem tem acesso ao repositório obtém a chave de produção do gateway de
  pagamento e a senha do banco. Trocar credenciais exige alterar o código e
  fazer novo deploy.
  Recommendation: Externalizar toda a configuração para variáveis de ambiente
  lidas em config/, com defaults só de desenvolvimento e um .env.example sem
  valores reais (Playbook P-01).

  F02 [CRITICAL] Hash de senha caseiro e reversível, com senha padrão "123456"

  File: src/utils.js:17-23
  File: src/AppManager.js:18, 68
  Catalog: AP-03 — Armazenamento Inseguro de Senhas
  Description: badCrypto(pwd) repete os 2 primeiros caracteres do base64 da
  senha e trunca o resultado em 10 caracteres. É uma codificação reversível e
  sem salt: senhas com o mesmo prefixo colidem. No checkout, badCrypto(p || 
  "123456") atribui a senha "123456" quando pwd não é enviado, e o seed grava
  pass = '123' em texto puro.
  Impact: Um vazamento da tabela users revela as senhas, ou o prefixo delas, de
  forma trivial. Contas criadas sem pwd ficam com uma senha que qualquer
  atacante conhece.
  Recommendation: Usar crypto.scrypt com salt aleatório e comparação via
  timingSafeEqual. Gerar uma senha aleatória quando pwd estiver ausente em vez
  de usar uma padrão, e aplicar o mesmo hash ao seed (Playbook P-07).

  F03 [CRITICAL] Número de cartão e chave do gateway impressos no log

  File: src/AppManager.js:45
  Catalog: AP-04 — Exposição de Dados Sensíveis
  Description: console.log(\Processando cartão ${cc} na chave
  ${config.paymentGatewayKey}`)` grava o número completo do cartão e a chave
  live do gateway em stdout a cada checkout.
  Impact: Os logs passam a conter dados de cartão (violação direta de PCI-DSS) e
  o segredo do gateway.
  Recommendation: Nunca logar cartão nem chaves. Se for preciso, registrar só os
  4 últimos dígitos, mascarados, pelo logger central (Playbook P-08 + P-14).

  F04 [CRITICAL] Relatório financeiro e exclusão de usuários sem autenticação

  File: src/AppManager.js:80, 131-137
  Catalog: AP-05 — Endpoints Perigosos sem Proteção / Autenticação Quebrada
  Description: GET /api/admin/financial-report expõe a receita por curso e os
  nomes dos alunos, e DELETE /api/users/:id apaga qualquer usuário. Nenhum dos
  dois verifica identidade ou perfil.
  Impact: Qualquer cliente anônimo lê dados financeiros e pessoais e apaga
  contas arbitrárias.
  Recommendation: Middleware de autorização com token vindo de variável de
  ambiente (ADMIN_TOKEN), respondendo 401 quando a credencial faltar (Playbook
  P-13).

  F05 [CRITICAL] God Class AppManager: conexão, schema, seed, rotas e regras

  File: src/AppManager.js:4-139
  Catalog: AP-06 — God Class / God Module
  Description: A mesma classe abre a conexão (new sqlite3.Database(':memory:'),
  linha 7), cria o schema e o seed (initDb(), 10-23) e registra todas as rotas
  com regra, SQL e resposta HTTP (setupRoutes(app), 25-138). Isso cobre cinco
  domínios.
  Impact: Nenhuma parte pode ser testada ou reutilizada isoladamente, e não há
  fronteira entre dados, regras e HTTP.
  Recommendation: Separar em config / database / models / services / controllers
  / routes, compostos em app.js (Playbook P-03 + P-04).

  F06 [HIGH] Regras de negócio de checkout e relatório dentro dos handlers

  File: src/AppManager.js:28-78, 80-129
  Catalog: AP-08 — Regra de Negócio nas Rotas / Fat Controllers
  Description: O handler de checkout (51 linhas) aprova o pagamento
  (cc.startsWith("4")) e cria usuário, matrícula, pagamento e auditoria. O
  handler do relatório (50 linhas) soma a receita e monta o JSON.
  Impact: Essas regras só podem ser testadas via HTTP e não podem ser
  reutilizadas.
  Recommendation: Extrair CheckoutService e ReportService e deixar controllers
  finos (Playbook P-04).

  F07 [HIGH] Banco instanciado dentro da classe, sem injeção de dependência

  File: src/AppManager.js:7
  File: src/app.js:8-10
  Catalog: AP-09 — Alto Acoplamento / Sem Injeção de Dependência
  Description: this.db = new sqlite3.Database(':memory:') fica no construtor, e
  os handlers usam this.db/self.db diretamente.
  Impact: Não dá para trocar o banco nem usar dublês de teste sem alterar a
  classe.
  Recommendation: Criar a conexão no composition root e injetá-la em models →
  services → controllers (Playbook P-03 / P-06).

  F08 [HIGH] Estado global mutável (globalCache, totalRevenue)

  File: src/utils.js:9-15, 25
  File: src/AppManager.js:59
  Catalog: AP-10 — Estado Global Mutável
  Description: globalCache é alterado a cada checkout por logAndCache() e nunca
  é lido. totalRevenue é exportado como variável mutável de módulo.
  Impact: O cache não tem limite e cresce a cada usuário (vazamento de memória).
  É estado oculto, compartilhado pelo processo inteiro.
  Recommendation: Remover o estado global (Playbook P-06).

  F09 [HIGH] Checkout não atômico e callback hell com contadores manuais

  File: src/AppManager.js:37-77, 50-63, 69-72
  File: src/AppManager.js:83-127, 86-98, 117-122
  Catalog: AP-11 — Escritas Multi-etapa Não Atômicas / Callback Hell
  Description: O checkout tem 6 níveis de callbacks e 4 INSERTs sem transação. O
  relatório usa contadores manuais (coursesPending-- / enrPending--) para saber
  quando responder.
  Impact: Se o INSERT de pagamento falhar, o usuário e a matrícula ficam
  gravados sem pagamento. A ordem do relatório depende de qual query termina
  primeiro.
  Recommendation: Promisificar o driver, reescrever com async/await e usar
  BEGIN/COMMIT/ROLLBACK (Playbook P-09).

  F10 [MEDIUM] Queries N+1 no relatório financeiro

  File: src/AppManager.js:92, 104, 106
  Catalog: AP-12 — Queries N+1
  Description: O relatório faz uma query de enrollments por curso e, para cada
  matrícula, uma query de users e uma de payments: 1 + C + 2·M queries no total.
  Impact: O custo cresce de forma linear com o número de matrículas.
  Recommendation: Uma única query com LEFT JOIN, agregando o resultado no
  service (Playbook P-05).

  F11 [MEDIUM] Validação de entrada fraca no checkout e na exclusão

  File: src/AppManager.js:35, 46
  File: src/AppManager.js:132
  Catalog: AP-14 — Validação de Entrada Ausente ou Fraca
  Description: O checkout só verifica se os campos existem. Com card numérico,
  cc.startsWith lança TypeError dentro do callback do sqlite3, fora do ciclo do
  Express, e isso derruba o processo. O e-mail não é validado, e :id é usado sem
  checar se é inteiro.
  Impact: Um único POST /api/checkout com "card": 4111 derruba a API inteira.
  Recommendation: Validador de tipos na borda do controller, respondendo 400
  (Playbook P-12).

  F12 [MEDIUM] Erros ignorados nos callbacks e formatos de erro inconsistentes

  File: src/AppManager.js:57, 92-93, 104, 106, 133-135
  Catalog: AP-15 — Tratamento de Erros Engolido / Inconsistente
  Description: err é ignorado nos callbacks de auditoria, enrollments, users,
  payments e DELETE. Nas linhas 92-93, um erro deixa enrollments como undefined
  e o .length seguinte lança exceção. O DELETE responde sucesso mesmo quando
  falha. Não há middleware de erro, e as respostas misturam texto e JSON.
  Impact: Falhas de banco viram crash do processo ou sucesso falso.
  Recommendation: Propagar os erros com async/await + next(err) até um
  middleware de erro central (Playbook P-10).

  F13 [MEDIUM] Exclusão de usuário deixa matrículas e pagamentos órfãos

  File: src/AppManager.js:133-135
  File: src/AppManager.js:14-15
  Catalog: AP-16 — Dados Órfãos / Integridade Referencial Ausente
  Description: O DELETE não trata enrollments nem payments, e as tabelas não
  declaram FKs. A própria resposta admite o problema ("ficaram sujos no banco").
  Impact: O relatório passa a listar alunos "Unknown" com receita de usuários
  que não existem mais.
  Recommendation: Apagar matrículas e pagamentos do usuário em transação antes
  de apagar o usuário, sem mudar status nem corpo da resposta (Playbook P-09).

  F14 [MEDIUM] Dependências transitivas deprecated do driver sqlite3

  File: package-lock.json
  Catalog: AP-DEP — APIs Deprecated / Obsoletas
  Description: sqlite3@5.1.7 traz pacotes que o npm marca como deprecated: glob
  e tar antigos (com vulnerabilidades conhecidas), inflight, rimraf < 4, npmlog,
  gauge, are-we-there-yet, prebuild-install e @npmcli/move-file.
  Impact: Avisos a cada npm install e mais superfície de vulnerabilidades na
  cadeia de build.
  Recommendation: Avaliar a migração para node:sqlite ou atualizar o driver
  (Playbook P-11). Fica fora do escopo estrutural.

  F15 [LOW] console.log como mecanismo de log

  File: src/app.js:13
  File: src/utils.js:13
  Catalog: AP-17 — print / console.log como Log
  Description: O banner de startup e [LOG] Salvando no cache usam console.log
  direto.
  Impact: Não há níveis de log nem controle central.
  Recommendation: Criar um módulo logger (Playbook P-14).

  F16 [LOW] Magic strings na regra de pagamento e nos status

  File: src/AppManager.js:46, 48, 108
  Catalog: AP-18 — Magic Numbers / Strings
  Description: A aprovação usa startsWith("4"), e os status "PAID"/"DENIED"

  Impact: Um erro de digitação em um status quebra o cálculo de receita sem
  nenhum aviso.
  Recommendation: Constantes nomeadas no model de pagamento (Playbook P-12).

  F17 [LOW] Nomenclatura ruim/enganosa

  File: src/AppManager.js:4, 29-33

  Recommendation: Renomear ao mover o código, mantendo os campos do payload, que
