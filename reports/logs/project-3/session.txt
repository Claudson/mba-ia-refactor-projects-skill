  F01 [CRITICAL] Secret key e senha SMTP no próprio código

  File: app.py:13
  File: services/notification_service.py:7-10
  Catalog: AP-01 — Credenciais / Segredos Hardcoded
  Description: O código traz app.config['SECRET_KEY'] = 'super-secret-key-123'.
  No serviço de e-mail, email_user = 'taskmanager@gmail.com' e email_password = 
  'senha123' também são valores fixos. A URI do banco (app.py:11) é fixa.
  Impact: Qualquer pessoa com acesso ao repositório obtém a chave de assinatura
  e a credencial SMTP.
  Recommendation: Ler os valores de um módulo config alimentado por variáveis de
  ambiente (python-dotenv) e documentá-los em .env.example (Playbook P-01).

  F02 [CRITICAL] Senhas com hash MD5 sem salt

  File: models/user.py:27-32
  File: seed.py:19, 26, 33
  Catalog: AP-03 — Armazenamento Inseguro de Senhas
  Description: As senhas são gravadas com hashlib.md5(pwd.encode()).hexdigest()
  e verificadas por comparação direta. O seed usa as senhas '1234', 'abcd' e
  'pass'.
  Impact: MD5 sem salt é revertido por rainbow tables. Afeta POST /users, PUT 
  /users/<id> e POST /login.
  Recommendation: Usar werkzeug.security.generate_password_hash /
  check_password_hash. Aceitar MD5 legado só no login, para migrar os hashes
  antigos (Playbook P-07).

  F03 [CRITICAL] Hash de senha exposto nas respostas da API

  File: models/user.py:21
  File: routes/user_routes.py:33, 85, 129, 209
  Catalog: AP-04 — Exposição de Dados Sensíveis
  Description: User.to_dict() inclui 'password'. Esse dict volta em GET 
  /users/<id>, POST /users, PUT /users/<id> e POST /login.
  Impact: Qualquer cliente recebe o hash MD5 de qualquer usuário.
  Recommendation: Tirar password da serialização pública (Playbook P-08).

  F04 [CRITICAL] Token falso no login e endpoints destrutivos sem autenticação

  File: routes/user_routes.py:52, 71, 134-151, 210
  File: routes/task_routes.py:225-238
  File: routes/report_routes.py:211-223
  Catalog: AP-05 — Endpoints Perigosos sem Proteção / Autenticação Quebrada
  Description:
  - O login devolve 'fake-jwt-token-' + str(user.id), que nunca é verificado.
  - Todos os DELETE são anônimos.
  - POST /users aceita role: 'admin' vindo do cliente.

  Impact: Qualquer cliente anônimo pode apagar usuários, tasks e categorias, ou
  se registrar como admin.
  Recommendation: Emitir no login um token assinado com itsdangerous e exigir
  token válido nos endpoints destrutivos (Playbook P-13).

  F05 [HIGH] Debug ligado em 0.0.0.0 e CORS irrestrito

  Strategy

  Reorganização no lugar. O projeto já era parcialmente em camadas, com models
  do ORM corretos. Mantive os models e acrescentei o que faltava: config,
  controllers, middlewares de erro e de autenticação, e a composition root. A
  lógica saiu das rotas.

  New Project Structure

  app.py                       entry point: create_app(Settings()) + 
  app.run(host/port/debug da config)
  app_factory.py               composition root: logging, config, CORS opcional,
  banco, blueprints, handlers de erro
  config.py                    Settings via env/.env (SECRET_KEY, ADMIN_TOKEN, 
  DATABASE_URL, CORS_ORIGINS, DEBUG...)
  database.py                  instância do SQLAlchemy + init_db (create_all 
  dentro da factory)
  .env.example                 todas as variáveis de configuração documentadas
  models/common.py             utcnow() (UTC naive, sem API deprecated) e 
  completion_rate()
  models/task.py               constantes, is_overdue, serializers, consultas e 
  agregações (GROUP BY / joinedload)
  models/user.py               serialização sem senha, hash werkzeug com 
  migração de MD5 legado
  models/category.py           validação de cor, serialização
  controllers/validators.py    validadores compartilhados (payload, int, data)
  controllers/task_controller.py | user_controller.py | category_controller.py |
  report_controller.py   casos de uso
  routes/task_routes.py | user_routes.py | category_routes.py | report_routes.py
  | system_routes.py      blueprints finos (só HTTP)
  middlewares/errors.py        AppError e subclasses + handlers centrais (sempre
  JSON {"error": ...})
  middlewares/auth.py          require_admin / is_admin_request (header 
  X-Admin-Token)
  services/auth_service.py     token de login assinado (itsdangerous)
  seed.py                      usa a app nova; senhas com hash forte
  Removidos: utils/helpers.py, utils/__init__.py e
  services/notification_service.py. Eram código morto, e o serviço ainda tinha
  credenciais SMTP no código. Também tirei do requirements.txt o marshmallow e o
  requests, que não eram usados.

  Findings Resolved

  - F01 AP-01 → segredos movidos para config.py. A senha SMTP saiu junto com o
    serviço morto.
  - F02 AP-03 → hash werkzeug (scrypt). O MD5 legado é aceito no login e
    regravado com hash forte; testei e funcionou.
  - F03 AP-04 → User.to_dict() não inclui mais password.
  - F04 AP-05 → token assinado no lugar do fake-jwt-token. Os DELETE exigem
    X-Admin-Token, e definir ou alterar o role admin/manager também.
  - F05 AP-07 → debug desligado por padrão, host 127.0.0.1, CORS só para origens
    configuradas.
  - F06 AP-08 → rotas com 1 a 3 linhas. A lógica foi para os controllers e
    models, e as categorias ganharam blueprint próprio.
  - F07 AP-09 → create_app(settings); o import não toca mais no banco.
  - F08 AP-14 → os validadores devolvem 400 em vez de 500 (prioridade, título,
    busca, body nulo, cor, active, tags, role).
  - F09 AP-15 → nenhum except: restante; o tratamento de erros é central e
    sempre em JSON.
  - F10 AP-12 → joinedload em /tasks e contagens com GROUP BY em stats, users,
    categories e summary.
  - F11 AP-13 → is_overdue, serializers e validações agora existem em um único
    lugar.
  - F12 AP-16 → Task.detach_category na mesma transação. Correção: o finding era
    impreciso. O backref do ORM já zerava category_id, então nunca houve
    órfãos. A errata foi adicionada ao relatório.
  - F13 AP-DEP → utcnow() com timezone.utc e db.session.get(). O seed roda limpo
    com -W error::DeprecationWarning.
  - F14 AP-17 → logging em vez de print. Os print do seed.py ficaram, porque são
    a saída de um script de linha de comando.
  - F15 AP-18 → constantes nomeadas nos models.
  - F16 AP-19 → nomes ruins trocados ao mover o código.
  - F17 AP-20 → imports, helpers, métodos e dependências mortos removidos.
  - F18 AP-21 → condicionais simplificadas e isinstance.

  Intentional Contract Changes

  - GET /users/<id>, POST /users, PUT /users/<id>, POST /login → o campo
    password saiu da resposta (expunha o hash).
  - DELETE /tasks/<id>, /users/<id>, /categories/<id> → exigem X-Admin-Token:
    401 com token ausente ou errado, 403 se ADMIN_TOKEN não estiver configurado.
    Antes, a exclusão era anônima.
  - POST /users com role ≠ user e PUT /users/<id> alterando o role → 403 sem
    token de admin, para impedir que qualquer um se torne admin.
  - POST /login → token agora é assinado; a chave da resposta continua a mesma.
  - POST /tasks (priority não inteiro), PUT /tasks/<id> (title: null), GET 
    /tasks/search?priority=abc, body ausente ou não-JSON → 400 em vez de
    500/415.
  - Cor fora do padrão #RRGGBB, active não booleano, name vazio e tags inválidas
    → 400. Antes eram aceitos ou derrubavam a aplicação.
  - Rotas inexistentes e erros HTTP do Flask → JSON {"error": ...} no lugar de
    HTML.
  - CORS → desabilitado por padrão; é preciso configurar CORS_ORIGINS.
